# 3D 명함 Phase 0 기술 검증 결과

> 이슈 #1245 스파이크의 측정 기록. 후속 이슈 #1246~#1249 착수 판단의 근거 문서다.
> 설계서는 별도 레포의 `plans/마이페이지_명함 지갑형 개편_설계.md` 를 참고.

- 작성자: 제옹(euijjang97)

## 무엇을 왜 쟀나

지갑형 명함 개편은 "카드를 3D 로 세우고 돌린다"는 전제 위에 서 있다. 설계서 §11 이 Phase 0 을
**게이트**로 못박은 이유이기도 하다 — 성공 기준을 못 채우면 서버 렌더 전환이나 2D 폴백을
재논의해야 한다. 자산 제작까지 끝난 뒤에 프레임워크 한계에 부딪히지 않도록, 설계서 §6 이 지목한
3대 불확실성만 먼저 실측했다.

| 축 | 질문 | 막히면 영향받는 이슈 |
|----|------|---------------------|
| 1. 온디바이스 합성 | 런타임에 엔티티를 조립할 수 있나 · 사진 텍스처 메모리 비용은 | #1246 · #1248 |
| 2. 한글 텍스트 메시 | 한글이 3D 텍스트로 제대로 서나 (자소 분리 · 폰트 폴백) | #1248 |
| 3. 2D 스냅샷 | 3D 씬에서 그리드용 2D 이미지를 뽑는 비용과 품질 | #1249 |

## Go / No-Go 판정

**설계서에는 숫자 기준이 없다.** §11 이 "성공 기준을 충족하지 못하면"이라고만 쓰여 있어,
아래 기준은 이번 스파이크에서 새로 정한 값이다. 측정 후에 끼워 맞추지 않도록 프레임 예산과
화면 진입 체감 기준에서 먼저 뽑았다.

| 항목 | 기준 | 실측 | 판정 |
|------|------|------|------|
| 한글 표본이 빈 메시로 떨어지지 않을 것 | 6종 전부 | 6/6 정상 | ✅ |
| NFC/NFD 폭 비 | 0.9 ~ 1.1 | 1.000 | ✅ |
| 이름 줄이 카드 가로(90mm)에 들어갈 것 | ≤ 90mm | 최대 27.54mm | ✅ |
| 웜 상태 카드 1장 합성 | ≤ 100ms | 31.01 ~ 54.08ms | ✅ |
| 사진 텍스처 1장 메모리 | ≤ 4MB | 0.90 ~ 0.91MB | ✅ |
| 반복 합성 누수 없을 것 | 10회 후 증가 ≈ 0 | -96 ~ -32KB | ✅ |
| 그리드 20장 스냅샷 배치 | ≤ 3s | 0.91 ~ 1.05s | ✅ |
| 스냅샷이 빈 화면이 아닐 것 | 불투명 픽셀 > 1% | 39.4% | ✅ |
| **3D 최초 진입 지연** | **≤ 1s** | **9.42 ~ 11.62s** | ❌ |

**판정: 조건부 Go.** 렌더·합성·한글 품질은 전부 기준을 넘겼고 No-Go 사유가 없다. 다만 첫 진입
지연 하나가 기준을 크게 벗어난다 — 이건 카드 조립 비용이 아니라 RealityKit 런타임 최초 초기화
비용이고, 시뮬레이터 측정치다(아래 「첫 진입 비용」 참고). **#1249 착수 전 실기기 1회 재측정과
워밍업 전략 결정을 조건으로 건다.**

## 측정 환경

- iPhone 17 Pro 시뮬레이터 (iOS 26.5) · Xcode 26.6 · Debug 구성
- `BusinessCardPresentationTests` 타겟, Swift Testing
- 표기한 범위는 **연속 2회 실행의 최솟값~최댓값**이다. 시뮬레이터 수치는 실행마다 흔들려서
  단일 값보다 범위가 정직하다.

## 축 1 — 온디바이스 합성

`MeshResource.generateBox` 로 카드 본체를 만들고 텍스트 메시 3줄(`Text_name` · `Text_part` ·
`Text_generation`)과 사진 평면(`PhotoPlane`)을 자식으로 붙였다. 설계서 §6 의 1~4 단계 중
2(텍스트 바인딩) · 3(사진 텍스처 → `UnlitMaterial` baseColor) · 4(파트별 악센트 컬러 룩업)를
프리미티브로 흉내 낸 것이다. 1단계(번들 USDZ 템플릿 로드)는 에셋이 없어 제외했다.

| 항목 | 값 |
|------|-----|
| **첫 합성** (RealityKit 최초 초기화 포함) | 9421.22 ~ 11622.30ms · 메모리 +19.5 ~ 20.3MB |
| **웜 합성** 10회 평균 (사진 포함) | 31.01 ~ 54.08ms |
| **웜 합성** 10회 평균 (사진 제외) | 27.02 ~ 39.49ms |
| 사진 텍스처 1장 몫 (512px) | 시간 +3.99 ~ 14.59ms · **메모리 926 ~ 932KB** |
| 10회 반복 후 메모리 증가 (사진 제외) | -96 ~ -32KB |
| USDZ 저장 | 성공 · 89.1 ~ 135.5ms · 257KB |
| 자식 엔티티 | 4개 |

### 읽어낸 것

1. **사진 텍스처는 싸다.** 512px RGBA 원본 크기가 정확히 1MB 인데 실측 몫이 0.93MB 다 —
   밉맵 없이 원본만 올라간다는 뜻이다. 설계서가 걱정한 "사진 텍스처 메모리"는 병목이 아니다.
   명함첩에 20장을 동시에 물려도 텍스처만으로는 20MB 선이다.
2. **엔티티 누수 없음.** 사진 없이 10회 반복 합성한 뒤 메모리 증가분이 **음수**다. 조립한
   엔티티가 참조 해제와 함께 정상 회수된다.
3. **첫 합성과 이후 합성이 200배 이상 차이 난다.** 이건 카드 비용이 아니라 런타임 초기화
   비용이다 — 아래 절에서 따로 다룬다.
4. **USDZ 저장은 설계서 §6 기준 필수 경로가 아니다.** 교환 페이로드에 USDZ 를 싣지 않기로
   했으므로 프로필 필드만 주고받고 수신 측에서 재합성한다. 이 축을 잰 건 공유·내보내기 같은
   후속 기능이 열려 있는지 확인하려는 것이고, 결과적으로 열려 있다.

## 축 2 — 한글 텍스트 메시

`MeshResource.generateText` 에 한글을 넣고 바운즈·정점 수·소요 시간을 표본별로 수집했다.
표본은 실명이 아니라 글자 형태를 고르게 훑는 더미다. 시간 값은 두 실행 중 하나를 실었다
(실행 간 편차가 커서 시간은 참고치이고, 이 축의 결론은 **바운즈와 정점 수**가 낸다 —
이쪽은 두 실행에서 완전히 동일했다).

### 폰트 6mm (실물 명함 이름 줄 크기)

| 표본 | 문자열 성격 | ms | 가로×세로 (mm) | 정점 | 글자당 정점 |
|------|------------|-----|---------------|------|------------|
| 일반 | 3글자 이름 | 1.04 | 14.74×5.24 | 1286 | 429 |
| 네글자 | 4글자 이름 | 3.71 | 19.70×5.24 | 1494 | 374 |
| 긴이름 | 5글자 이름 | 4.66 | 25.74×5.24 | 2498 | 500 |
| 혼용 | 한글·라틴·숫자·중점 | 6.64 | 27.54×5.24 | 3006 | 334 |
| 복잡자모 | 겹받침 (뷁뾻쭑) | 6.67 | 15.03×5.26 | 3568 | 1189 |
| NFD분해 | 자소 분해형 | 3.50 | 14.74×5.24 | 1286 | 429 |

### 폰트 50mm (스케일 민감도 대조군)

| 표본 | ms | 가로×세로 (mm) | 정점 |
|------|-----|---------------|------|
| 일반 | 3.69 | 122.85×43.70 | 1286 |
| 네글자 | 3.75 | 164.20×43.70 | 1494 |
| 긴이름 | 4.93 | 214.50×43.70 | 2498 |
| 혼용 | 6.00 | 229.47×43.70 | 3006 |
| 복잡자모 | 6.07 | 125.25×43.85 | 3568 |
| NFD분해 | 4.24 | 122.85×43.70 | 1286 |

### 읽어낸 것

1. **자소 분리 없음.** `"김유엠"` 의 NFC 형과 NFD(`decomposedStringWithCanonicalMapping`)
   형이 **정점 수까지 완전히 동일**하고 가로 바운즈 비가 1.000 이다. CoreText 가 조합형을
   정규화해서 처리한다는 뜻 — 서버나 파일시스템에서 분해형 문자열이 와도 메시가 깨지지 않는다.
   합성 전 NFC 정규화를 넣을 필요가 없다.
2. **폰트 폴백 정상.** 겹받침(`복잡자모`)이 두부(tofu)로 떨어지지 않고 오히려 글자당 정점이
   1189 로 가장 많다 — 복잡한 글리프가 실제로 그려지고 있다는 증거다.
3. **스케일 무해.** 6mm ↔ 50mm 에서 정점 수가 완전히 동일하고 바운즈만 선형 확대된다.
   수 mm 단위 극소 폰트에서 글리프가 무너질까 봐 잰 건데, 그런 현상은 없다.
4. **레이아웃 제약이 실제 리스크다.** 6mm 기준 `긴이름` 25.74mm, `혼용` 27.54mm 로 카드
   가로 90mm 안에 넉넉히 들어간다. 다만 이름+파트+기수가 한 영역에 모이면 겹칠 수 있으므로
   #1248 에서 컨테이너 프레임과 줄바꿈 정책을 정해야 한다.

## 축 3 — 2D 스냅샷

`RealityRenderer` (iOS 18+) 로 뷰 계층 없이 오프스크린 텍스처에 렌더하고 `MTLTexture` →
`CGImage` → `UIImage` 로 뽑았다. `ARView.snapshot` 이 아니라 이쪽을 쓴 이유는 유닛 테스트에서도
돌고, 카드 저장 시점에 배치로 구울 수 있기 때문이다.

| 항목 | 값 |
|------|-----|
| 512px 1장 | 158.94 ~ 169.30ms · PNG 12KB · 불투명 픽셀 39.4% |
| 256px × 20장 | 총 909.3 ~ 1046.5ms · **장당 45.47 ~ 52.33ms** · PNG 합계 88KB · 메모리 +10.6 ~ 10.7MB |

불투명 픽셀 39.4% 는 렌더가 빈 화면이 아니라 실제로 카드를 그렸다는 확인이다(배경은 투명).

**조건부 판정 근거**: 장당 45~52ms 는 스크롤 프레임 예산(16.7ms)의 3배다. 그리드에서 셀이
보일 때마다 렌더하면 스크롤이 끊긴다. 카드 저장/수신 시점에 한 번 구워 디스크에 캐시하고
그리드는 캐시된 이미지만 읽는 구조여야 한다 — 20장 배치가 1초면 수신 직후 백그라운드
굽기로는 충분하다.

## 첫 진입 비용

첫 합성 9.4~11.6초는 **카드 조립이 아니라 RealityKit 런타임 최초 초기화 비용**이다. 근거는
같은 조립을 이어서 10회 돌린 웜 평균이 31~54ms 라는 것 — 200배 이상 차이가 카드 내용에서
나올 수는 없다. 시뮬레이터 Metal 이 호스트 GPU 위에서 셰이더를 처음 컴파일하는 몫이 크다.

**이 수치를 실기기로 옮겨 읽으면 안 된다.** 시뮬레이터 Metal 경로는 실기기와 특성이 다르고,
실기기에서는 훨씬 짧을 가능성이 높다. 다만 0 은 아니다. 그래서:

- **#1249 는 첫 카드 렌더 전 로딩 상태를 반드시 노출한다.** 빈 화면으로 버티면 안 된다.
- **워밍업 지점을 정한다.** 마이페이지 진입처럼 3D 화면보다 한 단계 앞에서 더미 엔티티를
  한 번 합성해 두면 실제 진입 때는 웜 경로를 탄다.
- **실기기 1회 재측정이 #1249 착수 조건이다.** 이 문서의 모든 수치는 시뮬레이터 값이다.

## 이 스파이크가 검증하지 **않은** 것

- **베이스 USDZ 템플릿** — #1246 이 3D 자산 제작을 필요로 해 이번 범위에서 제외했다.
  설계서 §6-1 의 `Entity(named:in:)` 로드 경로를 타지 않았고, 본체는 `generateBox` ·
  사진 면은 `generatePlane` 으로 대체했다. 라운드 코너·재질·조명은 전혀 반영하지 않았다.
  실제 템플릿을 얹으면 정점 수와 렌더 시간이 올라간다.
- **실기기 성능** — 전부 시뮬레이터 수치다. 위 「첫 진입 비용」 참고.
- **프레임레이트** — 정적 렌더 비용만 쟀다. 회전 중 지속 fps 는 측정하지 않았다.
- **회전 인터랙션** — 검증 뷰는 `.realityViewCameraControls(.orbit)` 로 손쉽게 붙였을 뿐,
  설계서가 요구하는 제스처·관성·스냅은 #1247 소관이다.

## 재현 방법

```bash
cd UMCApp && make generate
make test SCHEME=BusinessCardPresentation 2>&1 | grep "SPIKE#1245"
```

**`make test` (기본 `SCHEME=UMCApp`) 로는 이 측정이 돌지 않는다** — 앱 스킴의 테스트 액션에
`BusinessCardPresentationTests` 가 들어 있지 않다. 반드시 스킴을 지정한다.

측정 수치는 전부 `SPIKE#1245` 접두사로 출력된다. 스위트는 `.serialized` 다 — 메모리 증가분이
프로세스 전역 `phys_footprint` 차이라서, 병렬로 다른 테스트가 RealityKit 을 만지면 수치가
오염되고 첫 합성 비용도 다른 테스트에 흡수돼 사라진다.

### 시뮬레이터가 불안정할 때

측정 중 두 종류의 환경 실패를 겪었다. 둘 다 코드 문제가 아니고, 시뮬레이터를 리셋하면 사라진다.

| 증상 | 조치 |
|------|------|
| `Mach error -308 (ipc/mig) server died` · `IDELaunchiPhoneSimulatorLauncher` | 아래 리셋 |
| `Test crashed with signal kill` (콜드 부팅 직후 1회, 재현 안 됨) | 아래 리셋 후 재실행 |

```bash
xcrun simctl shutdown all
killall -9 com.apple.CoreSimulator.CoreSimulatorService
xcrun simctl boot "iPhone 17 Pro"
```
